## The order, and why

Backup encryption comes first because the Drive upload must only ever carry ciphertext.

### 1. Encrypt the backups (the base for everything else)

- Encrypt each `.dump` as it is written, with AES-256-GCM in chunks, so a large file never sits in memory.
  A small header says the format and key version, so a later key change can still open old files.
- Key held in the protected data directory, plus a **recovery key** shown once at setup. Restore asks for
  whichever it has. The signing key is already kept there, so I follow the same pattern.
- The "read it back after writing" check still runs: it decrypts, then lists the dump.
- Tests: round trip, a flipped byte is caught, wrong key refused, an old plain backup can still be restored.
- **Done when** a backup on disk cannot be read without the key, and restoring one still works from scratch.

### 2. Google Drive upload

- Sign-in uses Google's **device flow**: the page shows a short code, an admin opens google.com/device on any
  phone or PC. That works on a server with no browser, which is the hospital's case.
- Upload the **already encrypted** file, resumable, newest first. Keep the last N on Drive.
- The Backups page shows last upload, last error, and a button to retry. No sync, no conflict handling, only
  "upload the files that have not gone yet". If the internet is down it simply waits for the next night.
- The Google token is stored encrypted, with the same key mechanism. Granted per person on the Access page
  like any other section.
- Tests use a fake Google server. One manual try with the real account at the end.
- **Done when** a nightly backup lands on Drive encrypted, and a restore from the Drive copy works on a clean
  install.

### 3. Finish the licence

- Enforce the equipment limit with a plain message on add and on import, and keep the licence's existing
  read-only rule as it is.
- Enforce modules for the sections you name.
- Put the public key into the Docker build (a build argument), and make the pipeline fail without it, as
  `release.yml` already does for the installer.
- Run a renewal and an expiry end to end on a clean install.
- **Done when** a licence with a cap and a module list changes what the software lets you do, and a Docker
  image built without the key will not build.

### 4. Encrypt images, and write down the rest

- **Photos and PM report files:** encrypt the stored bytes with a per-file nonce and a key version, and
  migrate what is there already. The migration is forward-only, so **I take a backup first**.
- **Database files:** a diagnostics check that says whether the data drive is encrypted, and a short guide
  for BitLocker and Linux. No claim beyond what it does.
- **PDFs:** per question 4.
- **Done when** a photo in the database is unreadable to anyone reading the table, and still shows on the
  page.

### 5. DevOps, if time is left

- Commit `Dockerfile.backend` and `Dockerfile.postgres` (still uncommitted).
- A pipeline step that builds both images and runs the container check I used today, then pushes to Docker
  Hub on a version tag, using a token held as a secret.
- A compose file for backend plus PostgreSQL, and the Kubernetes files I offered, with the password in a
  Secret and never in a file.
- A fixed-version tag scheme, and an image scan.
